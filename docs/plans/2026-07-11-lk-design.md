**Статус:** утверждён в брейншторме, готов к передаче на этап планирования
**Область:** страница `/lk` внутри хаба эзотерических сервисов (проект Esoteric / Astrix)

## 1. Контекст проекта (как всё устроено сейчас)

- **Стек:** FastAPI (Python 3.12, SQLAlchemy 2.0, Alembic) + Next.js 14 (App Router, JS/JSX),
  Docker + Nginx. Авторизация S2S через auth_service партнёрки.
- **Продукты работают чисто на клиенте.** Расчёты и статичные тексты живут в
  `frontend/app/content/<slug>`, бэкенд отвечает только за авторизацию, подписки и суточные лимиты
  Таро. Весь контент дня детерминирован по дате (одна дата → один результат).
- **ЛК уже существует** и защищён `ProtectedRoute` (внутри ЛК пользователь всегда залогинен):
  - `frontend/app/lk/page.jsx` — обёртка + метаданные.
  - `frontend/app/lk/LKClient.jsx` — текущая реализация: блок «Подписка» (статус, оплатить,
    отменить, выйти), сетка ссылок на 4 продукта (`PRODUCTS` из `products.config.js`), форма
    профиля (`name`, `birth_date`, `gender` через `GET/PATCH /api/v1/profile/me`).
  - `frontend/app/lk/lk.module.css` — стили ЛК.
- **Профиль на сервере:** `GET/PATCH /api/v1/profile/me` хранит `name`, `birth_date`, `gender`
  (таблица `user_profiles`). Тело PATCH: `{ name, birth_date, gender }` (любое поле nullable).
- **Объект `user` в `AuthContext`** содержит только `id, email, subscribed, subscribed_until`.
  Даты рождения в нём нет.
- **Freemium:** подписка берётся из `user.subscribed`. Пейвол — `components/ui/Paywall.jsx`.

### 1.1. Текущая фрагментация даты рождения (чиним в §6)

Дата рождения сейчас живёт в трёх независимых местах, которые могут разойтись:

| Место | Ключ / эндпоинт | Кто пишет/читает |
|---|---|---|
| Профиль на сервере | `/api/v1/profile/me` → `birth_date` | ЛК; частично гороскоп |
| localStorage гороскопа | `horoscope.birth` (ISO `YYYY-MM-DD`) | `content/horoscope/index.js` |
| localStorage нумерологии | `numerology.profile` (`{ date, name }`) | `content/numerology/index.js` |

Продукты читают сначала свой localStorage, профиль — как запасной вариант. Из-за этого смена даты
в одном месте не отражается в других. Плумбинг для «профиль как источник правды» частично уже есть
в `content/horoscope/index.js`: `fetchBirthFromProfile()`, `saveBirthToProfile()`,
`loadBirthLocal()`, `saveBirthLocal()`, `normalizeBirth()`.

## 2. Что строим (суть)

ЛК превращается из «страницы аккаунта» в **персональный дашборд дня** — живую витрину сегодняшнего
дня под конкретного пользователя, с ежедневным ритуалом «собери свой день». Плюс сохраняются
базовые функции кабинета.

Страница состоит из четырёх смысловых частей (сверху вниз):

1. **Дашборд дня** — четыре бесплатных «знака дня», агрегированных из продуктов, с прогрессом и
   отметкой «открыто / ещё нет» (гибридная модель, см. §5).
2. **Быстрые переходы в продукты** — сетка из 4 карточек (уже есть, оставляем).
3. **Единый профиль** — имя, дата рождения, пол. Редактируется в одном месте и влияет на весь сайт
   (см. §6). Здесь же чиним фрагментацию из §1.1.
4. **Аккаунт** — email, «Выйти», «Выйти со всех устройств».

**Ключевая идея дашборда (гибрид).** Блоки видны всегда (кабинет никогда не пустой), но у каждого
есть состояние «открыто / ещё нет» и общий прогресс дня. Это одновременно и полный дашборд, и
отражение активности пользователя, и мягкий стимул заходить каждый день.

**Весь дашборд бесплатный.** Все четыре блока используют только free-контент продуктов, поэтому
подписчик и бесплатный пользователь видят один и тот же дашборд. Рекламной плашки подписки на
дашборде нет (осознанное решение владельца).

## 3. Ключевые архитектурные решения (принято в брейншторме)

| # | Решение | Обоснование |
|---|---|---|
| **Нового бэкенда нет** | Дашборд собирается из уже существующих клиентских генераторов контента. Профиль и выход используют существующие эндпоинты. | Весь контент дня детерминирован по дате; профиль (`/profile/me`), выход (`/auth/logout`, `/auth/logout-all`) уже готовы. |
| **Гибридная модель дашборда** | Блоки показываются всегда; сверху прогресс «открыто X из 4»; у каждого блока статус. | Сочетает полноту (нет пустого экрана) и идею «показывать то, что открыл»; создаёт ежедневный ритуал и причину возвращаться. |
| **Дашборд только на free-контенте** | Берём бесплатные блоки продуктов (карта дня, число дня, настрой дня, лунный день). | Никакого пейвола в дашборде; одинаков для всех; не дублирует продуктовый freemium. |
| **Трекинг «открыто» в localStorage** | Факт открытия за сегодня хранится в браузере, сбрасывается по суткам МСК. Кросс-девайс синхронизации нет. | По образцу гостевых лимитов Таро (`content/tarot/guestLimits.js`). Бэкенд не нужен. Кросс-девайс — опциональное расширение (§11). |
| **Профиль — единый источник правды** | Дата рождения (и имя, пол) правится в ЛК и распространяется на весь сайт; браузерные кэши продуктов синхронизируются от профиля. | Делает профиль реально полезным и чинит фрагментацию §1.1. Это подключение существующего эндпоинта, а не новый бэкенд. |
| **Подписка вне скоупа этого документа** | Управление подпиской реализуют программисты отдельно. Claude Code существующий блок подписки в `LKClient` не трогает и не описывает. | Разделение зон ответственности по требованию владельца. |
| **История раскладов вне скоупа** | Сохранённые расклады/избранное не делаем в этой версии. | Требует новых таблиц в БД; отдельный крупный этап. |

## 5. Дашборд дня (детально)

### 5.1. Четыре блока и их источники данных

Все функции уже существуют в `frontend/app/content/*`. «Сегодня» вычисляется через `new Date()` в
TZ Europe/Moscow (`moscowDayKey`).

| Блок | Нужна дата рождения? | Источник данных | Что показываем |
|---|---|---|---|
| **Карта дня** | Нет | `getDayCard(today)` + `getText({ scenario:'day', number })` и `getText({ scenario:'advice', number })` из `content/tarot/index.js` | Название аркана (`card.ru`), короткое послание/совет дня |
| **Число дня** | Да | `buildForecast({ date: birth, horizon:'day' })` из `content/numerology/index.js` → `{ number, text, free:true }` | Число личного дня + бесплатный текст |
| **Настрой дня** | Да | `sign(birth)` из `content/horoscope/astro.js` → `getToday(sign.id, today).blocks`, блок с `id === 'mood'` (free) из `content/horoscope/index.js` | Настрой дня по знаку зодиака |
| **Лунный день** | Нет | `getLunar(today)` из `content/horoscope/index.js` → `{ lunarDay, phase, todayMeaning }` | Номер лунного дня, эмодзи фазы, значение дня |

`sign(birth)` возвращает объект `{ id, name, element, planet, range }`; для «настроя дня» нужен
`sign.id`. Функция `getToday` также возвращает `sky` (фаза, лунный день, планетарный день,
ретрограды) — для блока «настрой дня» это не требуется, но при желании часть неба можно вынести в
шапку в будущем (вне скоупа сейчас).

### 5.2. Состояния блока

Каждый блок имеет два состояния в рамках сегодняшнего дня:

- **Ещё не открыт:** карточка показывает название блока, лёгкую подводку-дразнилку и кнопку
  «Открыть …». Контент скрыт. Статус «ещё не открыто».
- **Открыт:** карточка раскрывает free-контент прямо в дашборде + ссылку «Открыть полностью в
  {продукт}». Статус — зелёная галочка «открыто».

Нажатие «Открыть» в дашборде раскрывает контент инлайн **и** отмечает блок открытым (см. §5.4).
Открытие того же блока в самом продукте тоже отмечает его (§5.5).

### 5.3. Прогресс дня

Шкала в шапке: «открыто X из 4», где X — число открытых сегодня блоков. По достижении 4 из 4
показать короткую завершающую фразу дня (текст — открытый вопрос §14; можно захардкодить одну
нейтральную фразу на старте).

### 5.4. Трекинг «открыто» (localStorage)

Новый модуль `frontend/app/lk/dayProgress.js`, по образцу `content/tarot/guestLimits.js`:

```
KEY = 'lk.day_opened'
Формат: { day: '<moscowDayKey>', opened: { card: true, number: true, mood: false, lunar: false } }
```

- `moscowDayKey` импортировать из `content/tarot/index.js` или `content/horoscope/astro.js`
  (обе экспортируют идентичную функцию).
- `getOpened()` — вернуть объект `opened` за сегодня; при смене дня вернуть пустой (авто-сброс).
- `markOpened(blockId)` — отметить блок открытым за сегодня.
- Идентификаторы блоков: `'card' | 'number' | 'mood' | 'lunar'`.
- Всё в `try/catch` (как в `guestLimits.js`), молча деградировать при недоступном localStorage.

Ограничение осознанное: состояние на устройстве, между устройствами не синхронизируется. Для
дашборда из детерминированного контента это приемлемо (контент один и тот же, теряется только
галочка). Кросс-девайс — опциональное расширение (§11).

### 5.5. Отметка открытия из продуктов

Чтобы «открыл карту дня в Таро» отражалось в ЛК, соответствующие free-экраны продуктов вызывают
`markOpened(...)` при показе своего дневного free-контента:

| Продукт (файл) | Вызов |
|---|---|
| `app/tarot/day/DayClient.jsx` (открытие карты дня) | `markOpened('card')` |
| `app/horoscope/TodayView.jsx` (показан блок mood) | `markOpened('mood')` |
| `app/horoscope/LunarView.jsx` (показан лунный день) | `markOpened('lunar')` |
| `app/numerology/forecast/ForecastClient.jsx` (горизонт «День») | `markOpened('number')` |

Вызовы делать в `useEffect` при фактическом показе free-контента, не при заходе на страницу
вслепую. `dayProgress.js` импортируется в продукты из `app/lk/` (общий модуль клиента).

### 5.6. Пустой профиль как онбординг

ЛК всегда залогинен, но дата рождения может быть не заполнена. Тогда:

- **«Карта дня» и «Лунный день»** работают всегда (дата не нужна).
- **«Число дня» и «Настрой дня»** показывают мягкое состояние «Укажи дату рождения, чтобы открыть»
  со ссылкой/якорем на секцию профиля (§6) прямо в этом же ЛК.

Так сам дашборд подталкивает заполнить профиль, а первый ввод даты (здесь или в любом продукте)
запоминается навсегда (§6).

## 6. Единый профиль (источник правды)

### 6.1. Правило

> Дату рождения сайт спрашивает **ровно один раз** — тогда, когда она впервые понадобилась (в
> продукте или в ЛК). Введённое сразу сохраняется в профиль (`/api/v1/profile/me`), и дальше все
> продукты берут её оттуда автоматически.

Из этого следуют ответы на типовые случаи:

- **Залогинен, дата в профиле есть** → продукты не спрашивают ничего, считают сразу.
- **Залогинен, даты в профиле нет** → продукт спрашивает один раз; первый ввод уезжает в профиль;
  больше не спрашивают.

### 6.2. Приоритет источников

Для залогиненного пользователя **профиль главнее localStorage**. Правило чтения даты продуктом:

1. Залогинен → взять `birth_date` из профиля (`fetchBirthFromProfile()`); при наличии
   синхронизировать локальный кэш продукта от профиля.
2. Не залогинен (гость на продуктовых страницах вне ЛК) → localStorage как раньше.

Профиль перезаписывается только при явной смене даты в ЛК или при первом вводе своей даты в
продукте. Расчёт «на другого человека» (например, ввод второй даты в нумерологической
совместимости) профиль **не** трогает.

### 6.3. Что делаем в коде

- **Секция профиля в `LKClient`** уже читает и пишет `/api/v1/profile/me`. Дополнительно: после
  успешного PATCH синхронизировать оба локальных кэша, чтобы продукты сразу увидели новую дату:
  - `horoscope.birth` ← `birth_date` (через `saveBirthLocal` из `content/horoscope/index.js`).
  - `numerology.profile` ← `{ date: birth_date, name }` (через `saveProfile` из
    `content/numerology/index.js`).
- **Нумерология** (`content/numerology/index.js` + её клиенты): при залогиненном пользователе
  предпочитать `birth_date`/`name` из профиля перед `loadProfile()` (сейчас берётся только
  localStorage). Гороскоп уже умеет читать профиль (`fetchBirthFromProfile`) — привести нумерологию
  к той же логике.
- **Опционально (упрощает жизнь):** вынести чтение/запись даты в один общий модуль
  (`frontend/app/lib/birthProfile.js`) и переиспользовать из гороскопа и нумерологии, чтобы не
  держать две реализации синхронизации. Не обязательно для MVP, но рекомендуется.

Цель приёмки: сменил дату рождения в ЛК → зашёл в матрицу/нумерологию/гороскоп → они считают по
новой дате без повторного ввода.

## 7. Быстрые переходы в продукты

Существующая сетка из `PRODUCTS` (`products.config.js`): Матрица, Нумерология, Таро, Гороскоп.
Оставляем как есть (ссылки на `/{slug}`). Нужна, потому что дашборд дня покрывает не всё:

новый макет, но по сути блок готов.

## 8. Аккаунт

Минимальная секция:

- **Email** — показ (`user.email` из `AuthContext`).
- **Выйти** — `logout()` из `AuthContext` (уже есть; `POST /api/v1/auth/logout`).
- **Выйти со всех устройств** — `POST /api/v1/auth/logout-all` (эндпоинт есть на бэкенде),
  затем локальная очистка и редирект как в `logout()`.

Вне скоупа (требует бэкенда, помечаем в §11): смена пароля, смена email, удаление аккаунта.

## 10. Состояния и крайние случаи

1. **ЛК всегда залогинен** (`ProtectedRoute`) — гостевого состояния внутри ЛК нет.
2. **Пустой профиль** — см. §5.6 (два блока работают, два просят дату).
3. **Смена суток МСК** — прогресс и статусы «открыто» сбрасываются автоматически (сравнение
   `day` с текущим `moscowDayKey`), контент дня пересчитывается сам.
4. **Существующий блок подписки** — вне скоупа. Разметку и логику подписки в `LKClient` не трогаем
   и не описываем; при пересборке страницы оставляем блок на месте как есть. Кнопку «Выйти», если
   она сейчас живёт внутри блока подписки, переносим в новую секцию «Аккаунт» (§8).
5. **Недоступный localStorage** — трекинг молча деградирует (блоки просто всегда «ещё не открыто»),
   контент при этом показывается.

## 11. Что вне скоупа (осознанно не делаем в этой версии)

- **Управление подпиской** — реализуют программисты отдельно; в документе не описано.
- **История сохранённых раскладов и избранное** — отдельный крупный этап с новой БД.
- **Кросс-девайс синхронизация «открыто»** — потребовала бы таблицу активности в БД.
- **Уведомления и напоминания** («напомнить открыть карту дня») — нужен канал доставки
  (email/telegram/push), отдельный этап.
- **Рекламная плашка подписки на дашборде** — по решению владельца не размещаем.
- **Смена пароля, смена email, удаление аккаунта** — требуют работы на бэкенде/auth-сервисе.
- **Время и место рождения** — продуктам не нужны (гороскоп через знак, матрица по дате).

## 13. Визуальный язык

Переиспользуем существующую дизайн-систему проекта: CSS-модули, токены из
`frontend/app/styles/theme.css` (пергамент/золото/тёмный мистический), компоненты
`components/ui/{Card,Button,Input}`. Дашборд-карточки — на базе `Card`. Статус «открыто» —
акцент/золото либо мягкий зелёный; «ещё не открыто» — приглушённая карточка с пунктиром и кнопкой.
Тон формулировок в UI — без длинного тире «—» в русских текстах (предпочтение владельца).
