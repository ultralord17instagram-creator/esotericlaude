**Дата:** 2026-07-03
**Статус:** утверждён в брейншторме, готов к передаче на этап планирования
**Продукт:** «Расклад Таро» внутри хаба эзотерических сервисов (проект Esoteric / Astrix)

## 1. Контекст проекта (как всё устроено сейчас)

- **Стек:** FastAPI (Python 3.12, SQLAlchemy 2.0, Alembic) + Next.js 14 (App Router, JS/JSX),
  Docker + Nginx. Авторизация — S2S через auth_service партнёрки (оффер паролей не хранит).
- **Продукты сейчас работают ЧИСТО НА КЛИЕНТЕ.** Каждый продукт = запись в
  `frontend/app/products.config.js` + папка `frontend/app/<slug>/` + генератор контента в
  `frontend/app/content/<slug>.js`. Никакой персистентности и обращений к БД у продуктов нет.
- **Общая оболочка:** `frontend/app/components/ProductPage.jsx` рисует линейный поток
  «форма → результат», где результат = `FreeResult` + (`PaidResult` если подписан, иначе `<Paywall/>`).
  Подписка берётся из `user.subscribed` (`AuthContext`).
- **«Толстые» продукты** (например, `matrix`) не используют универсальный `ProductPage`, а имеют
  собственный клиент (`MatrixClient.jsx`) — это допустимый и уместный паттерн.
- **Backend-слои (для user-scoped данных):** `domain/entities` (чистые dataclass) →
  `repositories/<x>_repo.py` (`SqlXRepository`, прячет SQLAlchemy) → `services/<x>_service.py`
  (`XService`) → `api/v1/routes/<x>.py` (тонкий роут, `Depends(get_current_user)` +
  `Depends(get_db_session)`). Ключ пользователя — `auth_user_id: UUID`.
- **Текущее Таро** (`frontend/app/tarot/*`, `content/tarot.js`) — заглушка: 22 аркана, один
  расклad «прошлое/настоящее/будущее», детерминированный сид от даты. Будет заменён.

## 2. Что строим (суть продукта)

«Расклад Таро» — это **один продукт с тремя сценариями гадания**:

| Сценарий | Карт | Ввод | Бесплатно | Платно / по подписке |
|---|---|---|---|---|
| **Карта дня** | 1 | нет | одна карта на сутки, **одна на всех** (включая подписчиков) | — |
| **Три карты** | 3 | выбор темы | базовая тема «Прошлое-Настоящее-Будущее» — **1 раз в сутки** | платные темы (Теневая сторона, Предназначение, Идеальный партнёр, Проклятие рода) + полное толкование |
| **Да / Нет** | 1 | текст вопроса | **3 вопроса в сутки** | без лимита у подписчиков |

**Колода:** 22 Старших аркана, **только прямое положение** (без перевёрнутых). У каждой карты —
номер (0–21), английское имя, русское название. Картинки — позже (пока только названия).

**Подписка** убирает суточные лимиты (кроме «Карты дня» — она одна для всех) и открывает
платные темы «Трёх карт» и полные толкования.

**Тексты толкований** — заранее заготовленные (AI генерирует один раз, не на лету). Тон для
чувствительных тем («проклятие рода») — мягкий, поддерживающий, без запугивания.

## 3. Ключевые архитектурные решения (принято в брейншторме)

| # | Решение | Обоснование |
|---|---|---|
| **Хранение состояния** | **Гибрид (вариант B).** Колода и заготовки текстов — статикой в репозитории. «Карта дня» — детерминированно от даты (сид), одинакова для всех без бэкенда. **Суточные лимиты — на бэкенде** (новая таблица + роуты). | Лимиты нельзя обойти очисткой localStorage — иначе платная механика не имеет смысла. Контент при этом остаётся простым и версионируется в git. |
| **Модель текстов** | **Модель 3.** Цельный текст на пару «тема + карта» + один вводный абзац на тему. Позиция (Прошлое/Настоящее/Будущее) — структурный подзаголовок, **текст от позиции не зависит**. | Тексты цельные и живые (не «конструктор из склеек»), объём разумный (~110 на «Три карты» вместо 330). |
| **Навигация** | **Вариант C.** Один вход «Расклад Таро» в каталоге сервисов → экран выбора сценария → под-роуты `/tarot/day`, `/tarot/three`, `/tarot/yesno`. Собственный `TarotClient` (как у matrix), не через `ProductPage`. | Концептуально это один продукт; под-роуты дают прямые ссылки и чистую историю браузера. |
| **Расклады как данные** | Сценарии и темы описываются конфигом `SPREADS` (см. §5). Код читает конфиг, а не хардкодит сценарии. | Добавить новый расклад = добавить объект в конфиг, без переписывания кода. |
| **Механика выбора** | **8 одинаковых рубашек** веером. Тап → случайное назначение карты из ещё не выпавших в этом раскладе (без дублей) → flip. «Карта дня» — **одна рубашка**, переворот открывает предопределённую сидом карту. | Показывать все 22 нет смысла (рубашки неотличимы). 8 — фиксированное число для однозначного дизайна. |
| **Логика Да/Нет** | У каждого аркана **фиксированный полюс ответа** (`yes`/`no`) в данных колоды. Текст вопроса на ответ **не влияет** (ответ даёт карта из заготовок); вопрос нужен для ритуала и для учёта лимита по факту отправки. Полюса **два: Да / Нет** (без «Возможно»). | Соответствует принципу «заготовки, а не генерация на лету». |
| **Наполнение текстами** | Структура закладывается с **плейсхолдерами**. Реальные ~160 текстов пишутся **отдельно, в другом чате** (вне скоупа этой реализации). | По решению владельца продукта. |

## 4. Модель данных: колода

Статический файл `frontend/app/content/tarot/deck.js`. 22 Старших аркана, прямое положение.

```js
export const DECK = [
  { number: 0,  en: 'The Fool',            ru: 'Шут',            yesno: 'yes' },
  { number: 1,  en: 'The Magician',        ru: 'Маг',            yesno: 'yes' },
  { number: 2,  en: 'The High Priestess',  ru: 'Жрица',          yesno: 'no'  },
  // ... 3–20 ...
  { number: 21, en: 'The World',           ru: 'Мир',            yesno: 'yes' },
```

- Полный список 22 арканов — в Приложении A.
- `yesno` — фиксированный полюс ответа для сценария «Да/Нет» (значения проставляются при наполнении).
- **Задел на будущее** (поля добавляются позже, сейчас не используются):
  `image` (путь к картинке), `arcana: 'major'` (для расширения до 78 карт),
  `reversedMeaning` (перевёрнутые значения). Структура колоды не зависит от `SPREADS`,
  поэтому переход на 78 карт / картинки / перевёрнутые не трогает конфиг раскладов.

## 5. Модель данных: конфиг раскладов (`SPREADS`)

Статический файл `frontend/app/content/tarot/spreads.js`. Это «гибкие данные» — источник правды
о сценариях. Конфиг задаёт правила (сколько карт, что бесплатно/платно), бэкенд их применяет.

```js
export const SPREADS = [
  {
    id: 'day',
    name: 'Карта дня',
    cardCount: 1,
    picksFromDeck: false,   // не выбирается — общая на сутки
    dailyForAll: true,      // одна на всех, детерминированно от даты (сид)
    positions: ['День'],
    themes: null,
    demo: false,            // показывается целиком
    tableCards: 1,          // одна рубашка
  },
  {
    id: 'three',
    name: 'Три карты',
    cardCount: 3,
    picksFromDeck: true,
    positions: ['Прошлое', 'Настоящее', 'Будущее'],  // структурные подзаголовки
    tableCards: 8,          // 8 рубашек в веере
    themes: [
      { id: 'ppf',       name: 'Прошлое, Настоящее, Будущее', paid: false, freeLimit: 1 },
      { id: 'shadow',    name: 'Теневая сторона',             paid: true  },
      { id: 'purpose',   name: 'Предназначение',              paid: true  },
      { id: 'partner',   name: 'Идеальный партнёр',           paid: true  },
      { id: 'ancestral', name: 'Проклятие рода',              paid: true, sensitive: true },
    ],
    demo: { freeCards: 1 }, // ЗАДЕЛ: без подписки открыта вводная часть + 1 позиция, остальное под пейволом
  },
  {
    id: 'yesno',
    name: 'Да / Нет',
    cardCount: 1,
    picksFromDeck: true,
    needsQuestion: true,    // требуется ввод вопроса
    positions: ['Ответ'],
    tableCards: 8,
    themes: null,
    freeLimit: 3,           // 3 вопроса в сутки бесплатно
    demo: false,
  },
]
```

Правила лимитов:
- `freeLimit` живёт **на теме** там, где есть темы («Три карты»), и **на спреде** там, где тем нет («Да/Нет»).
- Платные темы (`paid: true`) требуют подписки; суточного лимита у них нет — гейт по подписке.
- `dailyForAll: true` («Карта дня») — лимитов и учёта на бэкенде не требует вообще.

**Задел на будущее в схеме** (поля зарезервированы, пока не используются):
`secretCard: false` (доп. карта сверх `cardCount`), `reversedAllowed: false` (перевёрнутые).
Уровень/размер колоды берётся из `DECK`, а не из спреда — расширение до 78 карт не трогает `SPREADS`.

## 6. Модель данных: заготовки текстов (Модель 3)

Тексты — статикой в `frontend/app/content/tarot/`. Три независимых слоя заготовок:

**6.1. Карта дня** — `texts/day.js`: 22 текста (по одному на аркан).
```js
export const DAY_TEXTS = { 0: '…текст для Шута…', 1: '…', /* ...21 */ }
```

**6.2. Да/Нет** — `texts/yesno.js`: 22 текста (поддерживающий текст-ответ на аркан;
полюс yes/no берётся из `DECK.yesno`).
```js
export const YESNO_TEXTS = { 0: '…', 1: '…', /* ...21 */ }
```

**6.3. Три карты** — `texts/three.js`: для каждой темы — вводный абзац + текст на каждый аркан.
```js
export const THREE_TEXTS = {
  ppf:       { intro: '…вводный абзац темы…', cards: { 0: '…', 1: '…', /* ...21 */ } },
  shadow:    { intro: '…', cards: { /* 0..21 */ } },
  purpose:   { intro: '…', cards: { /* 0..21 */ } },
  partner:   { intro: '…', cards: { /* 0..21 */ } },
  ancestral: { intro: '…', cards: { /* 0..21 */ } },  // мягкий, поддерживающий тон
}
```

Объём полного наполнения: 22 (день) + 22 (да/нет) + 5×(1 intro + 22 карты) = **~160 текстов**.

> **Вне скоупа реализации:** сами тексты пишутся отдельно (другой чат). На этапе реализации
> файлы создаются со **структурой и короткими плейсхолдерами**, чтобы механика работала и было
> видно форматирование. Тон «Проклятия рода» — мягкий/поддерживающий — задаётся при наполнении.

## 7. Механика и потоки сценариев (frontend)

Общий компонент: `frontend/app/tarot/TarotClient.jsx` + под-роуты. Экран `/tarot` — выбор сценария
(3 карточки), ведёт на `/tarot/day | /tarot/three | /tarot/yesno`.

**Случайное назначение карт** (для `picksFromDeck: true`): при тапе по рубашке выбирается случайный
аркан из ещё не выпавших в этом раскладе (без дублей), рубашка переворачивается (flip).

**7.1. Карта дня (`/tarot/day`)**
- Одна рубашка. Карта предопределена детерминированным сидом от текущей даты
  (та же для всех пользователей и подписчиков; можно переиспользовать существующий `dayHash()`).
- Клик → переворот → карта + текст из `DAY_TEXTS`. Без лимитов, без бэкенда.

**7.2. Три карты (`/tarot/three`)**
1. Экран выбора темы (5 тем; платные помечены; заблокированы без подписки → ведут на пейвол/демо).
2. Выбранная бесплатная тема «ППБ»: проверка суточного лимита на бэкенде (см. §8) → если доступно,
   веер из 8 рубашек, пользователь выбирает 3 → flip → расклad из 3 позиций
   (подзаголовки Прошлое/Настоящее/Будущее) + вводный абзац темы. **Бесплатная тема показывается целиком.**
3. Платная тема: если подписан — полный расклad; если нет — **демо** (`demo.freeCards`), остальное под `<Paywall/>`.
   *(Точную механику демо владелец допилит позже — сейчас реализуется дефолт-заглушка, data-driven,
   меняется в одном месте.)*

**7.3. Да / Нет (`/tarot/yesno`)**
1. Поле ввода вопроса. По отправке — проверка лимита 3/сутки на бэкенде (подписчики — без лимита).
2. Веер из 8 рубашек, выбор 1 карты → flip.
3. Экран ответа: карта → крупно **Да / Нет** (из `DECK.yesno`) → поддерживающий текст из `YESNO_TEXTS`.
   *(Показывать сам вопрос сверху — на усмотрение дизайна.)*
4. По исчерпании лимита — сообщение «доступно завтра» / предложение подписки.

> **Визуальный дизайн** (стили, анимации, вёрстка веера/переворота) дорабатывается владельцем
> отдельно в Claude Design. Реализация закладывает структуру и рабочую механику, не финальный визуал.

## 8. Backend: лимиты и учёт использования

Единственная новая серверная часть. Соответствует существующим слоям проекта.

**8.1. Таблица `tarot_usage`** (Alembic-миграция)

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | UUID / bigint PK | |
| `auth_user_id` | UUID | пользователь (из `UserContext`) |
| `spread_id` | text | `'three'` / `'yesno'` |
| `theme_id` | text \| null | для «Трёх карт» (`'ppf'`); null для «Да/Нет» |
| `usage_date` | date | дата (в TZ проекта) |
| `count` | int | число использований за день |

Уникальный индекс: `(auth_user_id, spread_id, theme_id, usage_date)`.

**8.2. Слои**
- `domain/entities/tarot_usage.py` — dataclass `TarotUsageEntity`.
- `repositories/tarot_usage_repo.py` — `SqlTarotUsageRepository` (get/increment по ключу дня).
- `services/tarot_service.py` — `TarotService`: правило лимита (читает конфиг лимитов — см. ниже),
  учёт подписки (подписчик → без лимита), проверка + инкремент.
- `api/v1/routes/tarot.py` — роуты (`Depends(get_current_user)` + `Depends(get_db_session)`),
  зарегистрировать в `router.py`.

**8.3. Эндпоинты**
- `GET  /api/v1/tarot/limits` → текущий остаток по сценариям/темам для пользователя (для гейта UI).
- `POST /api/v1/tarot/usage` `{ spread_id, theme_id? }` → сервер проверяет подписку и лимит; если
  доступно — инкремент и `{ allowed: true, remaining }`; иначе `{ allowed: false, reason: 'limit'|'subscription' }`
  (или соответствующий HTTP-код). Клиент вызывает это **перед** тем, как дать выбрать карты.

**8.4. Лимиты — источник правды.** Числовые лимиты (`freeLimit`) заданы в frontend-конфиге `SPREADS`.
Бэкенду тоже нужно знать эти числа для применения. Решение на этапе планирования: либо продублировать
лимиты в backend-конфиге (простое, но два источника), либо отдавать лимиты бэкенду через общий
источник. **Рекомендация:** небольшой backend-конфиг `tarot_limits` (dict `spread_id/theme_id → limit`),
синхронизируемый вручную со `SPREADS`; для 3 сценариев это дешевле, чем шарить конфиг между стеками.

**8.5. Случайное назначение карт** остаётся на клиенте (не влияет на честность лимитов — лимит гейтит
сам факт расклада). Перенос назначения на сервер — возможное будущее ужесточение, не требуется сейчас.

**Анонимные (незалогиненные) пользователи:** учёт лимитов возможен только для аутентифицированных
(есть `auth_user_id`). Предполагается, что сценарии с лимитами доступны только залогиненным
(«Карта дня» — публична, детерминирована). **Уточнить на этапе планирования:** нужен ли доступ к
«Три карты (ППБ)» / «Да/Нет» без входа, и если да — мягкий localStorage-лимит как запасной вариант.
